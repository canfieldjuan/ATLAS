# PR-EOM-Render-DB

## Why this slice exists

The operator asked to continue the Render-hosting arc after PR #2217 landed.
The previous slice proved a slim `atlas_brain.main_eom` profile can boot without
the full Atlas/local-model surface, but it deliberately left the Render
candidate with `ATLAS_DB_ENABLED=false` until a follow-up selected a safe
Postgres mapping.

This slice wires only that persistence boundary. It does not deploy the
Blueprint, expose receivables mutations, connect the EOM time tracker, or change
customer/onboarding behavior.

### Problem-derived contract

- Root cause: The slim EOM Render candidate cannot safely turn database
  persistence on yet because Atlas's shared database pool accepts only split
  host/port/user/password settings, while Render Blueprints expose a managed
  Postgres dependency to services most directly as one generated connection
  string. Turning `ATLAS_DB_ENABLED=true` without teaching the pool that mapping
  would leave the candidate either pointing at local defaults or requiring
  hand-managed secret fragments.
- Correct fix must touch/change: Add a typed `ATLAS_DB_CONNECTION_STRING`
  setting to the shared database config; make the shared asyncpg pool and
  standalone connection path use that connection string when present while
  preserving the existing split host/port path; update `render.eom.yaml` to
  define the candidate EOM Postgres resource and map
  `ATLAS_DB_CONNECTION_STRING` from that database; turn DB persistence on only
  for the candidate; and add tests that prove the Render YAML mapping, config
  selection, asyncpg kwargs, and real EOM lifespan startup/shutdown path.
- Must not change: Do not run or alter migrations, enable the receivables API,
  add service bearer-token material, change the existing full Atlas entrypoint,
  change EOM time tracker deployment/configuration, choose customer-visible
  onboarding or Stripe behavior, or touch unrelated open PR lanes.

## Mechanism

`DatabaseConfig` gains an optional `connection_string` field loaded through the
existing `ATLAS_DB_` prefix as `ATLAS_DB_CONNECTION_STRING`. Its connection
helper returns asyncpg kwargs in one of two shapes: `{"dsn": ...}` when the
connection string is present, or the existing split host/port/database/user/
password kwargs when it is absent. The shared database pool uses that helper for
both `asyncpg.create_pool` and long-lived raw `asyncpg.connect` calls, so the
EOM profile and existing shared callers agree on the same typed connection
selection path.

`render.eom.yaml` remains a non-authoritative candidate file, but now includes
the candidate `atlas-eom-postgres` database and maps the private service's
`ATLAS_DB_CONNECTION_STRING` env var from that database's generated connection
string. DB persistence flips on for the candidate; migrations and the
receivables API stay off.

## Intentional

- This PR uses `ATLAS_DB_CONNECTION_STRING`, not a bare `DATABASE_URL`, so the
  EOM candidate stays inside Atlas's typed `ATLAS_*` configuration convention.
- The Render file is still named `render.eom.yaml`, not render dot yaml, so this
  branch remains a reviewable candidate rather than an auto-applied live
  Blueprint.
- The candidate database is dedicated to EOM (`atlas-eom-postgres`) instead of
  reusing an unspecified existing Atlas database, but the PR does not deploy or
  migrate it.
- The split host/port env placeholders are removed from the EOM candidate once
  the generated connection-string mapping exists, reducing secret fragments in
  the service config.
